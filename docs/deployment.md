# 배포 준비와 운영

현재 작업은 로컬 구현·검증까지 진행했으며 외부 배포는 하지 않았다.

## 로컬 실행

Node 22.17.1에서 검증했다. Node 22의 내장 SQLite는 실험적 경고를 출력한다.

```sh
npm ci
npm run check
npm start
# http://localhost:3001
```

`npm run dev`는 Vite 5173과 API 3001을 함께 실행한다. 이때 브라우저는 `http://localhost:5173`로 접속한다. `APP_ORIGIN`은 브라우저 Origin과 정확히 일치해야 한다. `127.0.0.1`과 `localhost`는 다르다.

`npm run build`는 `dist`에 웹 화면을, `dist-server`에 서버 JavaScript를 생성한다. `npm run start:production`은 컴파일된 서버를 실행하는 명령이다. 이 명령 자체가 NODE_ENV를 바꾸지는 않는다. 로컬 HTTP 검증에서는 개발 쿠키 설정을 유지한다. 실제 배포에서는 반드시 다음 환경 설정을 사용한다.

## 배포 환경 변수

| 변수 | 설정 |
|---|---|
| AI_API_BASE_URL | 제공받은 HTTPS API 기본 주소. `/v1`까지, 인증 정보·쿼리 없음 |
| AI_API_KEY | 제공받은 키. 서버에만 주입, 브라우저·빌드 변수에 넣지 않음 |
| AI_MODEL | 제공자가 안내한 이미지·도구 호출 지원 모델 ID |
| NODE_ENV | `production` |
| APP_ORIGIN | 공개 HTTPS Origin. 예: `https://parts.example.com` (끝 `/` 없음) |
| HOST | 컨테이너는 `0.0.0.0`, 직접 로컬 실행은 `127.0.0.1` |
| PORT | 기본 3001 |
| DATABASE_PATH | 지속 저장 가능한 경로. 기본 `.data/parts.sqlite` |
| AI_DAILY_REQUEST_LIMIT | 24시간 창의 분석 요청 한도. 기본 100, 각 요청 최대 2회 API 호출 |

실제 `.env`를 Git·이미지·공유 파일에 포함하지 않는다. 예제만 `.env.example`로 제공한다. 모델 ID에 bedrock이 들어 있어도 앱은 제공 API만 호출하며 AWS 권한은 필요 없다.

## 컨테이너와 HTTPS

Dockerfile은 빌드 단계와 런타임 단계를 분리하고, 런타임에서 일반 `node` 사용자로 동작한다. 컨테이너의 3001 포트는 compose에서 호스트 루프백으로만 공개한다. HTTPS 역방향 프록시를 앞에 둔다.

배포 담당자가 도메인과 TLS를 준비한 뒤 실행할 명령:

```sh
# .env에 실제 APP_ORIGIN=https://실제도메인 설정 후
# 아래 명령은 이번 작업에서 실행하지 않았다.
docker compose up --build -d
```

Caddy 설정 예시(도메인은 실제 값으로 변경):

```caddyfile
parts.example.com {
    request_body {
        max_size 42MB
    }
    reverse_proxy 127.0.0.1:3001
}
```

단일 Node 프로세스·단일 로컬 SQLite 볼륨으로 실행한다. 여러 replica가 같은 DB를 공유하는 구성은 지원하지 않는다. 다중 인스턴스가 필요하면 작업 잠금·큐·세션·한도를 공유 저장소로 옮겨야 한다. SQLite DB를 NFS에 두지 않는다.

서버는 임의 `X-Forwarded-For`를 신뢰하지 않는다. 프록시 뒤에서는 IP 한도가 프록시 단위로 합산된다. 익명 데모의 비용 상한을 보수적으로 제한하는 설정이며, 실제 사용자별 IP 제한이 필요하면 신뢰 프록시 범위를 별도 검토해야 한다.

## 운영 동작

- `GET /api/health`: 서버 응답과 사진 분석 설정 유무. API 제공자 실시간 가용성 검사는 아니다.
- 분석 동시 실행 2개, 분석 큐 최대 10개, 업로드 동시 처리 2개.
- 사진 분석: 세션당 20회/24시간, IP당 40회/24시간, 전체 기본 100요청/24시간. 스키마 재시도 포함 최대 200번 공급자 호출. 토큰/금액별 상한은 제공자 대시보드에서 별도로 설정한다.
- 생성 요청에 `Idempotency-Key`를 사용한다. 같은 키·같은 입력은 기존 결과를 재사용하며, 다른 입력은 409, 삭제한 요청의 재전송은 410이다. 키는 세션별로 24시간 보관한다. 브라우저는 네트워크 오류 후 같은 입력을 다시 제출할 때 키를 유지한다.
- 브라우저의 수정 요청은 `If-Match`로 버전을 확인해 오래된 화면의 덮어쓰기를 막는다. 같은 제품·부품의 개인 장착 기록은 중복 추가 대신 갱신한다.
- 생성 요청: 세션당 30회/시간, IP당 60회/시간. API 전체 IP당 240회/분.
- 256비트 임의 세션 쿠키, HttpOnly·SameSite=Strict, 배포 모드 Secure. 서버는 세션 해시만 보관한다. 요청 소유권과 CSRF 토큰·Origin을 모두 검사한다.
- JPEG/PNG/WebP 실제 디코딩, 25MP 제한, 장당 10MB·최대 4장, 전체·부품 1600px / 라벨 2400px 축소, EXIF 제거. AI에는 정규화된 사진만 전달한다.
- 사진 데이터는 대기 중 SQLite에 임시 저장하고 분석 종료 또는 기록 삭제 시 제거한다. 찾기 기록·세션은 최대 24시간, 1분 간격 정리. SQLite secure_delete 및 WAL checkpoint를 사용하지만 저장 매체의 물리적 복구 불가능 삭제를 보증하지 않는다.
- 재시작 시 대기 작업은 계속한다. 실행 중이던 작업은 결과 확인 불가 상태로 마무리하고 자동 재호출하지 않는다. 공급자에서 이미 청구됐을 수 있는 호출의 중복을 피한다.
- 분석 도중 기록을 삭제해도 완료 콜백이 기록을 되살리지 않는다. 이미 전송한 공급자 요청 자체를 취소하거나 공급자 저장 데이터를 제거하는 기능은 없다.
- 서버 로그에는 키, 업로드 사진, OCR 원문, 공급자 오류 본문을 쓰지 않는다.
- 기록 보관 정책을 지키려면 개인 DB를 장기 백업하지 않는다. 카탈로그 JSON과 코드는 별도로 백업할 수 있다.

## 현재 검증 범위와 제한

- HTTP API 통합 테스트, 사진 디코딩·소유권·CSRF·요청 제한·재시작 처리 검증 완료.
- 실제 제공 API를 통한 공개 사진 분석 및 Chrome 데스크톱·360px/390px 모바일 화면 검증 완료.
- 배포용 JavaScript 빌드와 Docker 이미지 빌드·로컬 기동 검증 완료. 운영 모드의 HTTP 상태, Secure 쿠키, SQLite 쓰기·읽기, 제품 선택, CSP와 Linux Sharp 이미지 처리까지 확인했다. 컨테이너는 일반 사용자로 실행되고 `.env`를 포함하지 않는다. 외부 HTTPS·DNS는 실제 배포 때 설정한다.
- 카탈로그는 13개 분야·405개 제품·111개 부품·487개 근거로 확장했다. [현재 범위](daily-life-expansion.md). 미등록 제품은 분야와 부품 이름·규격을 유지해 검색·문의로 안내한다.
- 웹 전체 자동 수집이나 실시간 검색 API는 연결하지 않았다. 실제 상품 링크는 검수 카탈로그에서 가져오며 외부 Google 검색 링크를 구분한다.
- 국내/해외/배송 미확인을 구분하고, 신규 판매 항목의 재고는 `unknown`이다. 내용 검수일과 재고 확인 시각을 분리한다. 이번 405개 카탈로그와 최신 코드로 Docker 빌드·운영 모드의 로컬 기동을 재검증했다. [검증 기록](predeployment-validation.md).
- 실제 실물 장착·누수·내열 검증은 하지 않았다. 개인 장착 기록은 검증 없이 공개 카탈로그 근거로 승격하지 않는다.

공개 배포 직전에는 실제 도메인·HTTPS 설정, 공급자 사용량 상한·보관 정책, 배포 환경에서의 이미지 처리 및 공급자 연결을 확인한다. 이번 작업은 계정·DNS·서버에 배포 변경을 만들지 않는다.
